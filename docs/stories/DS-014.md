# Story: Define Blueprint Schema and Validation

## Narrative
- **As a** factory operator
- **I want to** define sandbox configurations as validated YAML blueprints with a well-defined schema
- **So that** I can version-control, share, and validate sandbox definitions before creation — catching misconfigurations at validation time rather than mid-creation

## Acceptance Criteria

### AC-001: Blueprint YAML schema includes all required fields
The blueprint schema supports: `apiVersion` (string, required), `kind` (must be "Blueprint"), `metadata.name` (string, required), `metadata.description` (string, optional), `spec.image` (string, required), `spec.policy` (string, optional), `spec.providers` (list of strings, optional), `spec.mcp_servers` (list, optional), `spec.forwards` (list of port specs, optional), `spec.resources` (cpu/memory, optional), `spec.upload` (list of "local:remote" specs, optional).
- **Test:** `test_blueprint_schema_parses_full_spec_with_all_fields()`
- **Test:** `test_blueprint_schema_parses_minimal_spec_with_only_required_fields()`

### AC-002: Schema validated before sandbox creation
`darkshell blueprint validate <file>` validates a blueprint YAML and reports all errors. Validation runs before any side effects (no partial sandbox creation on invalid blueprint).
- **Test:** `test_blueprint_validate_rejects_missing_required_fields()`
- **Test:** `test_blueprint_validate_reports_all_errors_not_just_first()`

### AC-003: Validation errors reference YAML line numbers
When validation fails, error messages include the YAML line number and field path where the error occurred, so operators can locate the problem quickly.
- **Test:** `test_validation_error_includes_line_number_and_field_path()`

### AC-004: Unknown fields produce warnings, not errors (forward compatibility)
If a blueprint YAML contains fields not recognized by the current schema version, a warning is emitted but validation succeeds. This allows older DarkShell versions to partially process blueprints written for newer versions.
- **Test:** `test_unknown_fields_produce_warning_not_error()`

### AC-005: `apiVersion` is checked and must be `darkshell/v1`
The `apiVersion` field must be present and set to `darkshell/v1`. An unrecognized `apiVersion` produces an error suggesting the user upgrade DarkShell.
- **Test:** `test_invalid_api_version_rejected_with_upgrade_suggestion()`
- **Test:** `test_missing_api_version_rejected()`

### AC-006: MCP server entries validated per transport type
For `transport: bridge`, `command` is required and `url` is forbidden. For `transport: in-sandbox`, `command` is required and `env` is forbidden. For `transport: streamable-http`, `url` is required and `command` is forbidden. Violations produce field-specific errors.
- **Test:** `test_bridge_transport_requires_command_forbids_url()`
- **Test:** `test_in_sandbox_transport_requires_command_forbids_env()`
- **Test:** `test_streamable_http_transport_requires_url_forbids_command()`

### AC-007: Port forward specs validated for correct format
Port forward specs must match `[bind_address:]port` format where port is 1-65535. Invalid specs produce errors with the expected format.
- **Test:** `test_valid_port_forward_specs_accepted()`
- **Test:** `test_invalid_port_forward_spec_rejected_with_format_hint()`

### AC-008: Resource limit values validated
`spec.resources.cpu` must be a valid Kubernetes CPU quantity (e.g., "2", "500m"). `spec.resources.memory` must be a valid Kubernetes memory quantity (e.g., "4Gi", "512Mi"). Invalid values produce errors with valid examples.
- **Test:** `test_valid_resource_limits_accepted()`
- **Test:** `test_invalid_resource_cpu_rejected_with_examples()`
- **Test:** `test_invalid_resource_memory_rejected_with_examples()`

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-009 | Blueprint references image that can't be pulled | Schema validation passes (image existence is a runtime check in DS-015, not schema check). |
| EC-010 | Blueprint references provider that doesn't exist | Schema validation passes (provider existence is a runtime check in DS-015, not schema check). |
| EC-CUSTOM-001 | Blueprint YAML is empty file | Error: "Empty blueprint file. See `darkshell blueprint --help` for format." |
| EC-CUSTOM-002 | Blueprint YAML has valid YAML but wrong structure (e.g., a list instead of map) | Error: "Blueprint must be a YAML mapping, not a sequence. Expected `apiVersion`, `kind`, `metadata`, `spec`." |
| EC-CUSTOM-003 | Blueprint `metadata.name` contains characters invalid for sandbox names | Error: "Blueprint name 'X' contains invalid characters. Sandbox names must match [a-z0-9-]." |
| EC-CUSTOM-004 | Blueprint file is not valid YAML (syntax error) | YAML parse error with line number from serde_yaml. |
| EC-CUSTOM-005 | Blueprint has duplicate MCP server names | Error: "Duplicate MCP server name 'X' in blueprint. Each server must have a unique name." |
| EC-CUSTOM-006 | Blueprint `spec.upload` entry missing colon separator | Error: "Upload spec 'path' must be in format 'local:remote'. Got: 'path'." |

## Architecture Compliance Rules

| Rule | Source | Enforcement |
|------|--------|-------------|
| Blueprint is single source of truth for sandbox configuration | ADR-004 | Schema covers all sandbox configuration: image, policy, providers, MCP, forwards, resources, upload |
| Three new crates, not one mega-crate | ADR-006 | `darkshell-blueprint` is a separate crate |
| Blueprint schema must be forward-compatible | ADR-004 | Unknown fields warn, not error (AC-004) |
| Errors are domain knowledge, not strings | SOUL.md Section 5 | `ValidationError` enum with field path, line number, and fix suggestion |
| Make the wrong thing impossible | SOUL.md Section 2 | Transport-specific field requirements enforced by validation, not documentation |
| `#[non_exhaustive]` on enums that will grow | .claude/rules/rust.md | `McpTransport` enum is `#[non_exhaustive]` |
