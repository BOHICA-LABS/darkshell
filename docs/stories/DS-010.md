# Story: Add MCP Tool-Level Policy at Bridge Layer

## Narrative
- **As a** factory operator
- **I want to** restrict which MCP tools an agent can invoke by configuring `allowed_tools` and `denied_tools` in policy YAML
- **So that** I can limit agents to read-only tools and block destructive operations, even though port-forwarded MCP traffic bypasses the sandbox OPA proxy

## Acceptance Criteria

### AC-001: Bridge denies all tool calls by default when policy is configured
When a policy YAML includes an MCP endpoint block with `allowed_tools` or `denied_tools`, the bridge evaluates every incoming JSON-RPC `tools/call` request against the policy before forwarding to the MCP server. If no explicit allow/deny is configured for an MCP endpoint, all tools are allowed (backward-compatible).
- **Test:** `test_bridge_denies_unlisted_tool_when_allowed_tools_configured()`
- **Test:** `test_bridge_allows_all_tools_when_no_policy_configured()`

### AC-002: Tools can be allowlisted per MCP server
When `allowed_tools: [read_file, search]` is configured for an MCP server endpoint, only those tools are permitted. Any other tool call returns a JSON-RPC error response to the agent.
- **Test:** `test_bridge_allows_only_allowlisted_tools()`
- **Test:** `test_bridge_rejects_tool_not_in_allowlist_with_jsonrpc_error()`

### AC-003: Tools can be denylisted per MCP server
When `denied_tools: [delete_file, write_file]` is configured, those specific tools are blocked. All other tools are allowed.
- **Test:** `test_bridge_blocks_denylisted_tools()`
- **Test:** `test_bridge_allows_tools_not_in_denylist()`

### AC-004: Allowlist and denylist are mutually exclusive
If both `allowed_tools` and `denied_tools` are specified for the same MCP server endpoint, policy validation fails with an actionable error at load time, not at request time.
- **Test:** `test_policy_validation_rejects_both_allow_and_deny_for_same_server()`

### AC-005: Policy is evaluated per request at bridge layer
Each `tools/call` JSON-RPC request is individually evaluated against the tool policy. The bridge parses the `method` and `params.name` fields from the JSON-RPC request to determine the tool being called.
- **Test:** `test_bridge_evaluates_policy_per_request_not_per_connection()`

### AC-006: Denied tool calls are logged with structured fields
Every denied tool call emits a structured log event containing: sandbox name, MCP server name, tool name requested, deny reason (not in allowlist / in denylist), timestamp.
- **Test:** `test_denied_tool_call_emits_structured_log()`

### AC-007: Policy hot-reload updates tool restrictions without bridge restart
When the policy YAML is updated via `darkshell policy set`, the bridge picks up the new tool restrictions without requiring a bridge restart. The bridge watches for policy changes or is notified via a reload signal.
- **Test:** `test_bridge_applies_updated_tool_policy_without_restart()`

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-CUSTOM-001 | Tool name contains special characters or unicode | Tool name matched as exact UTF-8 string comparison. No glob/regex support in v1. |
| EC-CUSTOM-002 | JSON-RPC request is malformed (missing `method` or `params.name`) | Bridge returns JSON-RPC error (-32600 Invalid Request) without forwarding. Logged as parse error. |
| EC-CUSTOM-003 | `tools/list` request (not `tools/call`) | `tools/list` is always allowed regardless of policy. Policy only applies to `tools/call`. Agent needs to discover available tools. |
| EC-CUSTOM-004 | Empty `allowed_tools: []` list | No tools are allowed. All `tools/call` requests are denied. This is a valid deny-all configuration. |
| EC-CUSTOM-005 | Empty `denied_tools: []` list | No tools are denied. All `tools/call` requests are allowed. This is equivalent to no policy. |
| EC-CUSTOM-006 | Concurrent policy reload during request evaluation | Request uses the policy version that was active when evaluation started (no partial reads). Atomic swap via Mutex/RwLock. |
