# Story: Implement Blueprint-Based Sandbox Creation

## Narrative
- **As a** factory operator or DarkClaw orchestration engine
- **I want to** create a fully-configured sandbox from a single blueprint YAML file with `darkshell sandbox create --from blueprint.yaml`
- **So that** sandbox setup is declarative, reproducible, version-controlled, and reduced from 5+ manual commands to one

## Acceptance Criteria

### AC-001: Blueprint YAML orchestrates full sandbox creation
`darkshell sandbox create --from blueprint.yaml` creates a sandbox using the image specified in `spec.image`, applies the policy from `spec.policy`, attaches all providers listed in `spec.providers`, and configures port forwards from `spec.forwards`. All steps execute in sequence; the sandbox reaches Ready phase.
- **Test:** `test_blueprint_creates_sandbox_with_all_sections()`

### AC-002: MCP bridge servers are started from blueprint
When `spec.mcp_servers` includes entries with `transport: bridge`, the orchestrator starts MCP bridge daemons on the host for each server, port-forwards them into the sandbox, and auto-configures network policy entries. `darkshell mcp list <sandbox>` shows all servers as running.
- **Test:** `test_blueprint_starts_mcp_bridge_servers()`

### AC-003: In-sandbox MCP servers are configured from blueprint
When `spec.mcp_servers` includes entries with `transport: in-sandbox`, the orchestrator configures the sandbox to launch the MCP server as a subprocess inside the sandbox. The server inherits all sandbox restrictions (Landlock, seccomp, netns).
- **Test:** `test_blueprint_configures_in_sandbox_mcp()`

### AC-004: Resource limits are applied from blueprint
When `spec.resources` contains `cpu` and/or `memory` fields, the sandbox is created with corresponding k8s resource limits applied to the pod spec.
- **Test:** `test_blueprint_applies_resource_limits()`

### AC-005: Files are uploaded from blueprint
When `spec.upload` contains entries in `"local:remote"` format, the orchestrator uploads each specified directory during sandbox creation, equivalent to multiple `--upload` flags.
- **Test:** `test_blueprint_uploads_files()`

### AC-006: All referenced resources are validated before creation
Before creating the sandbox, the orchestrator validates that: the image is pullable, all named providers exist, the policy file is valid YAML and passes schema validation, and all MCP server commands are non-empty. If any validation fails, creation is aborted with an actionable error referencing the specific blueprint field.
- **Test:** `test_blueprint_validates_all_resources_before_creation()`

### AC-007: Partial creation is rolled back on failure
If any step fails after sandbox creation has begun (e.g., MCP bridge start fails), all previously completed steps are rolled back: the sandbox is deleted, bridge daemons are stopped, port forwards are removed, and policy entries are cleaned up. The error message reports which step failed and what was rolled back.
- **Test:** `test_blueprint_rolls_back_on_partial_failure()`

### AC-008: Blueprint creation completes within performance target
Blueprint sandbox creation with a locally cached image completes in under 60 seconds (NFR-004), including all MCP bridge startups, port forwards, and uploads.
- **Test:** `test_blueprint_creation_within_60_seconds()`

## Edge Cases
| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-009 | Blueprint references image that cannot be pulled | Fail fast with actionable error: "Image `ghcr.io/x/y:z` not found. Check registry access and image name." Abort before any sandbox creation. |
| EC-010 | Blueprint references provider that does not exist | Fail fast: "Provider 'github' not found. Create with: `darkshell provider create --name github --type github`" |
| EC-B01 | Blueprint YAML has syntax errors (invalid YAML) | Fail with parse error including line number and column from serde_yaml |
| EC-B02 | Blueprint has valid YAML but unknown fields | Fail with "Unknown field 'foo' in blueprint spec. Valid fields: image, policy, providers, mcp_servers, forwards, resources, upload" |
| EC-B03 | Blueprint specifies both `transport: bridge` and `transport: in-sandbox` for the same MCP server name | Fail with "Duplicate MCP server name 'perplexity'. Each server must have a unique name." |
| EC-B04 | Policy file referenced in blueprint does not exist on disk | Fail with "Policy file 'policies/factory-agent.yaml' not found. Provide an absolute path or a path relative to the blueprint file." |
| EC-B05 | MCP bridge port conflicts with an existing port forward | Bridge selects next available port (per EC-019). Log which port was selected. |
| EC-B06 | Blueprint `spec.image` is empty string | Fail with "`spec.image` is required. Specify a container image reference (e.g., `ghcr.io/org/image:tag`)." |

## Architecture Compliance Rules

| Rule | Source | Enforcement |
|------|--------|-------------|
| Blueprint is the single source of truth for sandbox configuration | ADR-004 | Blueprint YAML contains all fields needed; no implicit defaults that differ from explicit `sandbox create` flags |
| No modification to openshell-sandbox or openshell-server crates | ADR-001 | `git diff` of those crates must be empty |
| MCP bridge runs on host, not in sandbox | ADR-002 | Verify bridge PID files are on host; bridge subprocess runs with host credentials |
| All enhancements are additive — existing `sandbox create` unchanged | ADR-008 | `sandbox create --name X --from image:tag` without `--from blueprint.yaml` behaves identically to upstream |
| Dependency graph is acyclic | ADR-006 | `darkshell-blueprint` depends on `openshell-core` and `darkshell-mcp`; never on `openshell-sandbox` or `openshell-server` |
| Actionable error messages on every failure | NFR-014, SOUL.md Rule 5 | Every error includes what failed, which blueprint field caused it, and how to fix it |
