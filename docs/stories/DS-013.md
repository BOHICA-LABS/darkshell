# Story: Add MCP Tool Call Logging at Bridge Layer

## Narrative
- **As a** factory operator
- **I want to** see a structured audit log of every MCP tool invocation that passes through the bridge daemon
- **So that** I have full visibility into what MCP tools agents are using, what arguments they pass, and how long each call takes — especially since port-forwarded MCP traffic bypasses the sandbox proxy

## Acceptance Criteria

### AC-001: Every tool call through bridge is logged with structured fields
Each MCP `tools/call` JSON-RPC request that passes through the bridge produces a structured log event containing: server name, tool name, arguments (serialized), timestamp, and a unique request ID.
- **Test:** `test_bridge_logs_tool_call_with_server_name_and_tool_name()`
- **Test:** `test_bridge_log_includes_arguments_and_timestamp()`

### AC-002: Response is logged with summary and duration
When the MCP server responds, the bridge logs: request ID (correlating to the request log), response status (success/error), response summary (truncated to configurable max length, default 512 chars), and call duration in milliseconds.
- **Test:** `test_bridge_logs_response_with_duration_and_summary()`
- **Test:** `test_bridge_truncates_response_summary_at_configured_limit()`

### AC-003: Logs are written in structured JSON format
Log entries are structured JSON (via `tracing` with JSON formatter) suitable for ingestion by log aggregation tools. Each entry includes sandbox name as a top-level field for filtering.
- **Test:** `test_bridge_log_entries_are_valid_json()`
- **Test:** `test_bridge_log_entries_include_sandbox_name()`

### AC-004: Log integrates with sandbox watch event stream
MCP tool call log events are emitted as events that `darkshell sandbox watch` (DS-016) can consume and display in its real-time stream. Events use the event type `mcp.tool_call`.
- **Test:** `test_mcp_tool_call_events_available_to_watch_stream()`

### AC-005: Failed tool calls are logged with error details
When an MCP server returns a JSON-RPC error response, the log entry includes the error code and error message from the response, in addition to the standard fields.
- **Test:** `test_bridge_logs_error_responses_with_code_and_message()`

### AC-006: Logging does not add measurable latency to tool calls
The logging overhead is less than 1ms per tool call (within NFR-003's 10ms bridge overhead budget). Logging is non-blocking — log entries are sent to a channel, not written synchronously.
- **Test:** `test_bridge_logging_overhead_under_one_millisecond()`

### AC-007: `tools/list` requests are logged at debug level only
Discovery requests (`tools/list`) are logged at debug level to avoid noise in production logs. Only `tools/call` requests produce info-level log entries.
- **Test:** `test_tools_list_logged_at_debug_level_only()`

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-CUSTOM-001 | Tool call arguments contain very large payload (>1MB) | Arguments logged with truncation at configurable limit (default 4096 chars). Full arguments not stored. |
| EC-CUSTOM-002 | MCP server response is binary / non-UTF-8 | Response summary shows `<binary response, N bytes>` instead of attempting string conversion. |
| EC-CUSTOM-003 | Bridge processes 1000+ tool calls per second | Log channel is bounded (capacity 10,000). If full, new entries drop with a counter for dropped events. Never blocks the request pipeline. |
| EC-CUSTOM-004 | Tool call is denied by policy (DS-010) | Denied calls are logged separately (by DS-010). If a call passes policy, it is logged by this story's logging. No double-logging. |
| EC-CUSTOM-005 | MCP server hangs and tool call times out | Duration logged as the time until timeout. Response logged with status "timeout". |
| EC-CUSTOM-006 | JSON-RPC batch request with multiple tool calls | Each tool call in the batch logged as a separate event with the same batch ID field. |
