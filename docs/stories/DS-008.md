# Story: Implement MCP bridge daemon (stdio-to-HTTP)

## Narrative
- **As a** factory operator (or DarkClaw orchestration engine)
- **I want to** connect MCP servers to sandboxes with a single command that starts a managed bridge daemon, handles credential injection, and auto-configures port forwarding
- **So that** AI agents inside sandboxes can use MCP tools (Perplexity, Tavily, GitHub, etc.) without manual proxy setup and without credentials ever entering the sandbox

## Acceptance Criteria

### AC-001: Bridge daemon starts an MCP server subprocess and exposes it as an HTTP endpoint
When the bridge daemon is started with a command (e.g., `npx -y @anthropic/perplexity-mcp`), it spawns the MCP server subprocess, communicates via stdio (stdin/stdout JSON-RPC), and exposes the server as an HTTP endpoint on `127.0.0.1:<port>`.
- **Test:** `test_bridge_starts_mcp_server_and_exposes_http()`

### AC-002: Bridge selects an available port starting from 9100
The bridge auto-selects a port starting from 9100, incrementing until an available port is found via `check_port_available()`. The selected port is recorded in the registration file.
- **Test:** `test_bridge_selects_available_port()`

### AC-003: Bridge translates HTTP requests to stdio JSON-RPC and back
Incoming HTTP POST requests to the bridge endpoint are translated to JSON-RPC messages on the MCP server's stdin. Responses from the server's stdout are translated back to HTTP responses.
- **Test:** `test_bridge_translates_http_to_jsonrpc()`

### AC-004: Bridge auto-configures port forwarding into the sandbox
After starting the HTTP endpoint, the bridge automatically creates an SSH port forward (`-L`) from the sandbox to the bridge port, using the existing `ForwardSpec` and port forward infrastructure.
- **Test:** `test_bridge_auto_creates_port_forward()`

### AC-005: Agent inside sandbox can reach MCP server via localhost:<port>
Once the bridge and port forward are established, an agent inside the sandbox can make HTTP requests to `localhost:<port>` and receive MCP tool responses.
- **Test:** `test_agent_reaches_mcp_via_localhost()`

### AC-006: Credentials injected from provider system into MCP server subprocess
The bridge retrieves credentials from the gateway provider API and injects them as environment variables into the MCP server subprocess. The agent process never sees the raw credential values.
- **Test:** `test_bridge_injects_credentials_from_provider()`

### AC-007: Credential environment variables are not visible from inside the sandbox
An `exec` command inside the sandbox cannot read the MCP server's environment variables. Credentials exist only in the host-side bridge daemon's subprocess.
- **Test:** `test_credentials_not_visible_in_sandbox()`

### AC-008: Bridge daemon auto-restarts MCP server on crash
When the MCP server subprocess crashes (pipe closure, non-zero exit), the bridge restarts it within 5 seconds using exponential backoff (1s, 2s, 4s). Maximum 3 restart attempts before giving up with an error.
- **Test:** `test_bridge_restarts_server_on_crash()`

### AC-009: Bridge logs each restart event with structured tracing
Each MCP server restart is logged with: sandbox name, server name, restart attempt number, backoff duration, and crash reason (exit code or signal).
- **Test:** `test_bridge_logs_restart_events()`

### AC-010: Bridge daemon writes PID and state to registration file
The bridge writes a registration file at `~/.config/darkshell/mcp/<sandbox>-<server>.yaml` containing: sandbox, server_name, transport, command, bridge_pid, forwarded_port, status.
- **Test:** `test_bridge_writes_registration_file()`

### AC-011: Bridge daemon cleans up on shutdown (SIGTERM)
When the bridge receives SIGTERM, it: (1) kills the MCP server subprocess, (2) removes the port forward, (3) removes the registration file. Cleanup completes within 5 seconds.
- **Test:** `test_bridge_cleans_up_on_sigterm()`

### AC-012: Bridge daemon force-killed after 10 seconds if graceful shutdown fails
If the bridge doesn't exit within 5 seconds of SIGTERM, it can be SIGKILL'd. Stale PID files are detected and cleaned on next startup.
- **Test:** `test_bridge_sigkill_after_timeout()`

### AC-013: Bridge handles port conflict by trying next port
When port 9100 is occupied, the bridge tries 9101, 9102, etc. until an available port is found. The selected port is recorded in the registration file and communicated to the port forward setup.
- **Test:** `test_bridge_handles_port_conflict()`

### AC-014: Bridge handles OAuth authentication flows on host side
When an MCP server requires interactive authentication (OAuth browser flow), the bridge handles the flow on the host side. The sandbox is never involved in authentication.
- **Test:** `test_bridge_handles_oauth_on_host()`

### AC-015: Bridge supports multiple MCP servers per sandbox
Multiple bridge instances can run simultaneously for the same sandbox, each on a different port, each managing a different MCP server.
- **Test:** `test_bridge_multiple_servers_per_sandbox()`

### AC-016: Bridge startup failure produces actionable error
When the MCP server command fails to start (binary not found, permission denied, etc.), the error includes: what command was attempted, the failure reason, and how to fix it.
- **Test:** `test_bridge_startup_failure_actionable_error()`

### AC-017: Bridge registration file removed on clean shutdown
When the bridge stops cleanly (SIGTERM or MCP server max-retries exhausted), the registration YAML file is removed. No orphaned registration files remain.
- **Test:** `test_bridge_removes_registration_on_shutdown()`

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-007 | MCP server subprocess crashes during agent operation | Bridge detects pipe closure, restarts server within 5s with backoff (1s, 2s, 4s). Agent receives 503 during restart window. After 3 failed restarts, bridge logs error and stops. |
| EC-008 | MCP server requires interactive OAuth browser flow | Bridge handles OAuth flow on host-side. Opens browser for user. Sandbox never involved in auth. Token cached for subsequent bridge starts. |
| EC-019 | Port conflict when auto-allocating bridge port | Bridge selects ports starting from 9100, increments via `check_port_available()`. If all ports in range exhausted, error: "No available ports in range 9100-9199 for MCP bridge." |
| EC-050 | MCP server produces malformed JSON-RPC response | Bridge returns HTTP 502 Bad Gateway with body: `{"error": "MCP server returned invalid JSON-RPC", "detail": "<parse error>"}` |
| EC-051 | Provider API is unavailable when bridge starts | Error: "Cannot retrieve credentials: gateway provider API unavailable. Check gateway status with: darkshell status" |
| EC-052 | Provider exists but requested credential key is missing | Error: "Provider 'perplexity' exists but credential 'PERPLEXITY_API_KEY' not found. Set with: darkshell provider create --name perplexity --credential PERPLEXITY_API_KEY=<value>" |
| EC-053 | Bridge started for a sandbox that no longer exists | Error: "Sandbox '<name>' not found. Available sandboxes: <list>" |
| EC-054 | Two bridges started for same sandbox+server name | Second start detects existing registration file, checks if PID is alive. If alive: error with PID. If stale: clean up and start fresh. |
| EC-055 | MCP server writes to stderr (warnings, debug output) | Bridge captures stderr and logs it at debug level via tracing. Does not affect HTTP responses. |
| EC-056 | Network drops between bridge and sandbox (port forward breaks) | Port forward SSH process exits; bridge detects and logs error. Does not attempt to re-establish (that's the CLI layer's responsibility via DS-009). |
| EC-057 | MCP server takes > 30 seconds to become ready | Bridge waits up to 60 seconds for first successful JSON-RPC `initialize` handshake. After 60s, error: "MCP server did not respond to initialize within 60s." |

## Architecture Compliance Rules

| Rule | Source | Enforcement |
|------|--------|-------------|
| MCP bridge runs on host, not in sandbox | ADR-002 | Bridge daemon is a host-side process; sandbox sees only HTTP via port forward |
| Credentials never enter the sandbox | ADR-002, NFR-007 | Credentials injected into host-side subprocess env only; verify via exec into sandbox |
| Port-forwarded traffic bypasses sandbox proxy | ADR-010 | Compensating controls: bridge-layer policy (DS-010), MCP logging (DS-013), credential isolation (this story) |
| Auto-restart within 5 seconds | NFR-011 | Backoff: 1s, 2s, 4s. Max 3 retries. Verified by test. |
| Bridge latency overhead < 10ms | NFR-003 | In-process async HTTP handler; no serialization to disk. Benchmark in test. |
| Enhancements in new crate | ADR-001, ADR-006 | All code in `darkshell-mcp` crate; no upstream crate modifications |
| Strictly acyclic dependency graph | Architecture Section 2 | `darkshell-mcp` depends on `openshell-core` only; never on `openshell-sandbox` or `openshell-server` |
| Actionable error messages | NFR-014 | Every BridgeError variant includes what, why, and fix suggestion |
