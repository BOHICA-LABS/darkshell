# Story: Support In-Sandbox stdio MCP Servers

## Narrative
- **As a** factory operator
- **I want to** run filesystem-only MCP servers (like Tally) inside the sandbox as subprocesses
- **So that** the MCP server inherits all sandbox restrictions (Landlock, seccomp, netns) and does not require host-side bridge infrastructure or external network access

## Acceptance Criteria

### AC-001: Agent spawns MCP server inside sandbox via exec
An agent (or operator) can start an MCP server inside the sandbox using `darkshell sandbox exec <name> -- <mcp-server-command>`, and the server runs as a subprocess within the sandbox, communicating via stdio with the agent process.
- **Test:** `test_in_sandbox_mcp_server_starts_via_exec()`

### AC-002: In-sandbox MCP server inherits all sandbox restrictions
The MCP server process running inside the sandbox is subject to the same Landlock filesystem policy, seccomp syscall filters, and network namespace isolation as any other sandbox process. No additional permissions are granted.
- **Test:** `test_in_sandbox_mcp_server_blocked_by_landlock()`
- **Test:** `test_in_sandbox_mcp_server_has_no_external_network()`

### AC-003: Blueprint supports `transport: in-sandbox` for MCP servers
A blueprint YAML can declare an MCP server with `transport: in-sandbox`, specifying the command to run. During sandbox creation, the server binary is expected to be present in the container image (pre-baked, not installed at runtime).
- **Test:** `test_blueprint_in_sandbox_transport_validates_correctly()`

### AC-004: In-sandbox MCP server works for filesystem-only tools
An MCP server that only accesses the sandbox filesystem (e.g., Tally for code findings) functions correctly inside the sandbox. The server can read and write files within Landlock-permitted directories.
- **Test:** `test_in_sandbox_mcp_server_reads_writes_permitted_directories()`

### AC-005: In-sandbox server documented as requiring pre-baked binary
When a blueprint references `transport: in-sandbox` and the command binary is not found in the sandbox, the error message explains that in-sandbox MCP servers must be pre-baked into the container image and suggests updating the Dockerfile.
- **Test:** `test_in_sandbox_missing_binary_error_suggests_dockerfile_update()`

## Verification Properties

| ID | Property | Type | Tool |
|----|----------|------|------|
| VP-001 | In-sandbox MCP server process inherits identical Landlock ruleset as parent process | proof | Manual audit — Landlock `restrict_self()` applies to process and all children |
| VP-002 | In-sandbox server cannot escalate privileges beyond sandbox boundary | proof | seccomp `PR_SET_NO_NEW_PRIVS` is inherited by child processes (kernel guarantee) |

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-CUSTOM-001 | In-sandbox MCP server attempts outbound network request | Request blocked by network namespace isolation. Server sees connection refused/timeout. |
| EC-CUSTOM-002 | In-sandbox MCP server tries to read `/etc/shadow` or other Landlock-denied path | Read blocked by Landlock. Server receives EACCES. |
| EC-CUSTOM-003 | In-sandbox MCP server binary requires dynamic libraries not in image | Server fails to start with shared library error. Error surfaced via exec exit code and stderr. |
| EC-CUSTOM-004 | In-sandbox server crashes during agent operation | Agent's stdio pipe closes. Agent must handle EOF on MCP connection (agent's responsibility, not DarkShell's). |
| EC-CUSTOM-005 | Blueprint declares `env` keys for in-sandbox transport | Error at validation: "In-sandbox MCP servers cannot receive host credentials. Use `transport: bridge` for servers requiring API keys." |

## Architecture Compliance Rules

| Rule | Source | Enforcement |
|------|--------|-------------|
| MCP server inherits all sandbox restrictions when running in-sandbox | ADR-002 (consequence) | In-sandbox is the alternative to host bridge; kernel guarantees restriction inheritance |
| No modification to sandbox runtime | ADR-001 | In-sandbox servers use existing sandbox process model; no changes to Landlock/seccomp/netns |
| Blueprint schema must be forward-compatible | ADR-004 | `transport` field uses enum; `#[non_exhaustive]` for future transport types |
| Sandbox mutability model: tools pre-baked, not runtime-installed | Architecture Section (Sandbox Mutability Model) | In-sandbox MCP servers must exist in container image; cannot install at runtime |
