# Story: Add Rsync Delta Upload with Tar Fallback

## Narrative
- **As a** DarkClaw orchestration engine (or operator)
- **I want to** upload only changed files to a sandbox via rsync-over-SSH with automatic fallback to tar when rsync is unavailable
- **So that** iterative development cycles on large workspaces (2GB+) complete in seconds instead of minutes, without breaking compatibility with minimal sandbox images

## Acceptance Criteria

### AC-001: --rsync flag triggers rsync-over-SSH transfer
When `darkshell sandbox upload <name> <local> [dest] --rsync` is invoked, the CLI uses `rsync -azP --delete` over the existing SSH ProxyCommand transport to transfer only changed files.
- **Test:** `test_rsync_upload_transfers_only_changed_files()`

### AC-002: Rsync uses the same SSH ProxyCommand transport as tar
The rsync invocation uses `--rsh "ssh -F <config>"` pointing to the same SSH config that upstream tar uploads use. No new network paths are created.
- **Test:** `test_rsync_uses_proxy_command_transport()`

### AC-003: Fallback to tar when rsync is absent in sandbox
When rsync is not installed in the sandbox image, the CLI detects the absence (via `ssh -T <host> which rsync`), logs a warning ("rsync not available in sandbox, falling back to tar upload"), and performs a standard tar upload.
- **Test:** `test_rsync_absent_falls_back_to_tar()`

### AC-004: Rsync transfer is resumable after interruption
If an rsync transfer is interrupted mid-stream, the next `--rsync` upload resumes correctly, transferring only the remaining changed files without corruption.
- **Test:** `test_rsync_interrupted_transfer_resumes()`

### AC-005: Symlinks are followed by default with opt-out
By default, rsync follows symlinks (`-L` flag). A `--no-follow-symlinks` flag disables this behavior, preserving symlinks as-is in the sandbox.
- **Test:** `test_rsync_follows_symlinks_by_default()`
- **Test:** `test_rsync_no_follow_symlinks_flag()`

### AC-006: Upload without --rsync flag uses existing tar behavior
The default `darkshell sandbox upload <name> <local>` (no `--rsync`) behaves identically to upstream `openshell sandbox upload`. No regression in existing behavior.
- **Test:** `test_upload_without_rsync_flag_uses_tar()`

### AC-007: Progress reporting is compatible with rsync transfer
When both `--rsync` and progress reporting are active, the progress bar displays rsync's transfer progress (bytes, rate). When progress is suppressed (piped/non-TTY), rsync output is also suppressed.
- **Test:** `test_rsync_progress_compatible()`

## Edge Cases
| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | rsync binary not present in sandbox image | Detect absence via `which rsync`, warn user ("rsync not available in sandbox '<name>'. Falling back to tar upload. To enable rsync, add it to your sandbox base image."), fall back to tar |
| EC-002 | rsync transfer interrupted mid-stream (network drop, Ctrl-C) | Partial transfer state is safe for rsync to resume on next invocation. No corrupted files in sandbox. |
| EC-013 | Symlinks in upload source directory | Default: follow symlinks (`-L`), upload the target file content. With `--no-follow-symlinks`: preserve symlinks as-is in sandbox. Document both behaviors in CLI help. |
| EC-R01 | Local directory is empty (no files to sync) | rsync completes successfully with 0 bytes transferred. No error. |
| EC-R02 | rsync available on host but SSH connection fails | Report SSH connection failure with actionable message ("SSH connection to sandbox '<name>' failed. Check gateway status with: darkshell status"). Do not fall back to tar (SSH failure affects both). |
| EC-R03 | rsync on host and rsync in sandbox have incompatible versions | rsync protocol negotiation handles version mismatch. If incompatible, rsync exits non-zero; fall back to tar with warning including version information. |
